Coding · how to not get stuck

Find the bug. Then make the next one easy to find.

Two skills that compound: a repeatable way to hunt down the cause of a bug, and a way to lay out code so the cause is obvious next time — for you, and for Claude reading it cheaply.

Find the root causePart 1 · the method

A bug is a gap between what you expected and what happened. The whole game is finding where reality first diverges from your mental model. Don't guess and change things at random — that turns one bug into three. Observe, narrow, then fix. Here's the loop, every time:

  1. Read the error — actually read it
    The error message and stack trace usually hand you the answer. Read it top to bottom: the top line is where it blew up; scan down for the first line in your file (e.g. shop.js:42) — that's your starting point. The message names the kind of failure (undefined is not a function, 404, permission denied).
  2. Reproduce it reliably
    A bug you can trigger on demand is half-fixed. Find the exact steps. Does it happen every time, or only sometimes? Every item, or one? Sometimes usually means timing/async or bad data; always means logic.
  3. Say expected vs actual out loud
    "I expected the image to load; instead I see the emoji." Now you know the gap is "the img URL isn't being used." Naming the gap points at where to look.
  4. Bisect — cut the problem in half
    The core skill. Drop a console.log (or print) at the midpoint of the path and ask: is the data correct here? If yes → the bug is downstream. If no → it's upstream. Move your log halfway again. In a few steps you've cornered the exact line. This beats staring at code every time.
  5. Ask "what changed?"
    If it worked yesterday, something changed. git log to see recent commits; mentally (or with git bisect) find the last commit where it worked. The diff since then contains your bug 90% of the time.
  6. Fix the cause, not the symptom — then guard it
    Patching the symptom (hide the error, retry blindly) leaves the cause to bite again. Fix the actual cause, then add a small guard so it can't silently return: a fallback, a check, or a clear error message.
The one habit that matters most

When stuck, resist editing code. Instead add one observation (a log, a breakpoint) that splits the unknown in half. You are not trying to fix yet — you're trying to locate. Fixing is easy once you know exactly where.

Structure for findabilityPart 2 · so bugs surface

A big codebase isn't hard because it's big — it's hard when you can't guess where a thing lives. Good structure means you (or Claude) jump to the right file in one search instead of reading everything. That's also the token saver: Claude debugs by searching; clear names and small, single-purpose files mean it finds the cause in one or two lookups, not by reading the whole repo.

One file, one job —so the file name predicts the bug
If you can describe a file in one sentence, it's right-sized. escrow.js handles escrow, nothing else. A bug in releasing funds? You already know the file.
Names you can grep —findable beats clever
releaseEscrowToSeller() is searchable and self-explaining. handle2() is a future mystery. Name for the person searching at 2 a.m.
Keep files small —~200–300 lines
A 2,000-line file costs more to read (more tokens, more scrolling) and hides bugs in the noise. Split by responsibility when it grows.
One source of truth per thing —no scattered copies
Your THB→Robux price math lives in one function, imported everywhere. Five copies = five places to fix and four you'll forget.
Group by feature once it grows —not by file type
Early on, flat is fine. Past ~15 files, fold into folders by feature (/deals, /payments, /admin) so related code sits together.
Errors carry context —where + what
throw new Error("releaseEscrow: deal 84 has no funded amount") tells you the file, the case, and the data. throw "error" tells you nothing.
A map at the root —orient in 10 seconds
A short README / CLAUDE.md listing what each folder does. It's the first thing Claude reads; it's how a big repo stays cheap to navigate.
The findability test

Read a bug report — "refund button does nothing" — and ask: can I name the file it's probably in? If yes, your structure is doing its job. If you'd have to search blindly, that's the signal to split and rename.

Logging at the boundaries

Log where data enters and leaves your system — an API call in, a payment out, a write to the database. When something breaks, these logs show you which side of the boundary went wrong, so bugs half-announce themselves before you even start hunting.

A real huntPart 3 · the method, applied

Watch the loop run on an actual RoShop-shaped bug. Notice: zero random edits — just observations that cut the unknown in half.

"The shop shows an emoji instead of the item's image."
1 · Expected vs actual
Expected: the knife image. Actual: the 🧉 emoji. Gap: the img URL isn't being used. So either there's no URL, or there is one and it fails to load.
2 · Reproduce / narrow
Is it every item or one? → Only "Eternal III". That points at the data, not the rendering code (the code works for every other item).
3 · Bisect with two observations
Open Console: any red errors? Open the Network tab, reload: did an image request 404? And log the item: console.log(item) — does it even have an img field?
4 · The split decides it
Two possible findings: (a) the item has no img field → the cause is the Firestore data, upstream. (b) it has one but Network shows a 404 → the URL is wrong (wrong raw.githubusercontent path or filename). Either way you now know the cause exactly — no guessing.
5 · Fix the cause, keep the guard
Case (a): add the img field in Firestore. Case (b): fix the raw URL. The guard already exists by design — the shop falls back to the emoji when img is missing or broken, which is exactly why you saw an emoji and not a crash. Good guards turn bugs into graceful degradation.

That's the entire discipline: expected vs actual → reproduce → bisect with observations → locate the cause → fix + guard. It scales from a one-page shop to a codebase you can't hold in your head.

Ask Claude so it's cheapbonus · fewer tokens, faster fixes

When you hand a bug to Claude, the difference between a slow, expensive answer and an instant one is how you frame it. Give the three things that let it skip straight to the right file:

The cheap bug report

1. The exact error — paste the Console/terminal text, don't paraphrase.

2. Where — the file, or the page/feature (shop.js, "the admin image tab").

3. Expected vs actual — "I expected X, I got Y."

“Console says Cannot read 'img' of undefined in shop.js when I open the shop; I expected the item to render.” → Claude goes straight to the line.

“the shop is broken” → Claude has to read everything to find it. More tokens, slower, vaguer.
