Lesson 11 · Systems & scale

The cloud's biggest breach is a setting.

You run on the cloud — Firebase backs RoShop. Here's the uncomfortable truth of cloud security: the spectacular breaches usually aren't clever hacks. They're a checkbox someone left in the wrong state. Which is good news, because checkboxes you can control.

~8 min · interactive · your RoShop lesson · builds on Lessons 2 & 9

Moving to the cloud doesn't remove security work — it moves it. The provider secures the building; you secure your apartment in it. Getting that split wrong is how "an open S3 bucket" ends up in the news every other week.

The cloud security model — defined

shared responsibility
The cloud provider (AWS, Google, Firebase) secures the infrastructure — the hardware, the network, the platform. You secure your configuration and data — who can access what, your rules, your secrets. Most breaches are on the customer's side of that line.
IAM (identity & access management)
The system that decides which identities (users, services) can do which actions on which resources. It's access control (Lesson 9) at cloud scale. Getting IAM right — least privilege — is the core of cloud security.
misconfiguration
The #1 cause of cloud breaches: a storage bucket set to public, a database with no auth, debug mode on, an overly-broad permission. Not a hack — a setting.
secrets management
API keys, database passwords, service credentials — stored in a dedicated secret manager or environment variables, never in code or a public repo. (You've seen this in Lessons 3 & 9; in the cloud it's everywhere.)
security rules (Firebase)
Your app's access control, written as rules: who can read/write which data. A wide-open rule is the cloud-era equivalent of SQL injection — anyone can read or wreck everything.

The classic cloud breaches — all settings

    
Open storage bucket → millions of records public to anyone with the URL. No-auth database → wide open to the internet. Over-broad IAM role → one compromised key can touch everything. Secret in a public repo → bots scan GitHub for committed keys within minutes. None of these are "hacks" — they're misconfigurations a checklist prevents.

  


  
The defender's cloud checklist

  

    
Default-deny, then least privilege

    
Start with everything locked. Grant each user/service the minimum it needs, nothing more. Your Firebase rules and IAM roles both live by this.

    
Never commit secrets

    
Keys in env vars / secret managers; .env in .gitignore. Bots scrape public repos for keys constantly — a committed key is compromised in minutes.

    
Lock down storage & databases

    
No public buckets unless truly intended; auth required on every database; verify the defaults (cloud defaults are not always safe).

    
Enable logging & alerts

    
Know who accessed what. You can't respond to a breach you can't see (Lesson 12's territory).

  


  
Recap

  
Cloud security is shared responsibility: the provider secures the platform, you secure your config and data — and most breaches are on your side. The villains are misconfiguration (public buckets, no-auth databases, broad roles) and committed secrets. The defense is the same idea as everywhere: default-deny, least privilege, secrets out of code. Your Firebase rules are this lesson made concrete — get them right and you've done the hard part.


  

    
Check yourself

    
A startup's entire user database leaks. The cause: their cloud storage bucket was set to "public." Whose responsibility was that, under the shared model?
