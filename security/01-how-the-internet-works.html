Lesson 1 · Foundations

How the internet really works.

You can't defend a thing you can't picture. Before any attack or defense makes sense, you need the map: what actually happens between typing a web address and the page appearing. It's a relay race of small messages, and every handoff is a place something can go wrong.

~7 min · interactive · no prior knowledge needed

Type atlas into your browser and a page appears in half a second. It feels like magic, but it's a precise sequence of steps across machines you'll never see. Security lives in those steps — so let's walk every one.

The big idea: everything is messages

The internet has no "connection" in the way a phone call does. There's no single wire held open between you and a website. Instead, your request is chopped into small packets, each labeled with a destination, and each forwarded hop-by-hop across the network like postcards through a postal system. They can take different routes, arrive out of order, and get reassembled at the end. That postcard model is the whole foundation.

The terms, defined

IP address
The numeric "street address" of a machine, like 142.250.72.14. Every device online has one. Packets are addressed to IPs, not names.
DNS (Domain Name System)
The internet's phone book. It turns a human name (google.com) into an IP address. Your computer asks a DNS server "what's the IP for this name?" before it can send anything.
packet
A small chunk of your data wrapped in addressing info (where it's from, where it's going). Big things — a page, a video — are split into many packets.
TCP
The protocol that makes packets reliable. It numbers them, confirms each arrived, re-sends lost ones, and reassembles them in order. It starts with a "handshake" (a three-message hello) to set up the exchange.
port
A numbered door on a machine. One server can run many services; the port says which one you want. Web traffic uses 80 (HTTP) and 443 (HTTPS). Open ports are doors — and every door is something a defender must account for.
HTTP / HTTPS
The language browsers and web servers speak. HTTP is plain text (anyone on the path can read it). HTTPS is the same language inside an encrypted tunnel (TLS) — the S is for Secure, and it's why the padlock matters.

Every hop is a handoff, and every handoff is a place to listen, lie, or block. Security is the study of defending the handoffs.

Why this map is the whole course in miniature

Look back at the journey and you can already see where later lessons live. DNS can be poisoned (you get sent to the attacker's IP instead of the real one). HTTP can be read or altered by anyone on the path — which is why cryptography (Lesson 3) wraps it in HTTPS. Open ports are entry points a firewall (Lesson 6) decides to allow or deny. The server at the end runs code that might have web vulnerabilities (Lesson 5). You haven't learned those attacks yet — but you now have the map they happen on.

Defender's lens

A defender's instinct, applied to this lesson: every place data changes hands is a place to verify trust. Is this really the DNS answer I expected? Is this really the server's certificate? Is this port supposed to be open? Security isn't one wall — it's a question asked at every handoff.

Recap

The internet moves your data as addressed packets, hop by hop. DNS turns names into IP addresses; TCP makes the delivery reliable; ports pick the service; HTTP(S) is the language. The plain version (HTTP) is readable by anyone on the path — the encrypted version (HTTPS) is not. Hold this map in your head; everything from here hangs on it.
