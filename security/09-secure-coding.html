Lesson 9 · Systems & scale

Writing code that holds.

You build web apps, so this lesson is practical, not theoretical. The industry boiled the most common, most damaging code flaws down to one famous list — the OWASP Top 10 — and almost all of them trace back to a handful of habits you can actually adopt.

~9 min · interactive · the coder's lesson · builds on Lesson 5

The OWASP Top 10 is the security world's "these are the bugs that keep getting people breached" list, maintained by a non-profit (the Open Worldwide Application Security Project). You don't need to memorize all ten — you need the patterns behind them, because the same few habits prevent most of the list.

The recurring villains — defined

injection
Untrusted input treated as code (SQLi, XSS from Lesson 5). Fix: parameterize and escape — data is data, never code.
broken access control
The #1 issue on the modern list. The app checks who you are but not what you're allowed to do — so user A can open user B's data by changing an ID in the URL. Fix: check authorization on every request, server-side.
security misconfiguration
Default passwords, debug mode on in production, an open cloud bucket, verbose error messages leaking internals. Fix: secure defaults, lock down config, hide internal errors from users.
vulnerable dependencies
You imported a library with a known hole. Most modern code is mostly other people's code. Fix: track your dependencies, update them, watch for advisories.
cryptographic failures
Storing passwords in plain text, weak/old algorithms, secrets hard-coded in the source. Fix: salt+slow-hash passwords (Lesson 4), use TLS, keep secrets out of code.
identification & auth failures
Weak passwords allowed, no rate-limiting on login, broken session handling. Fix: MFA, rate limits, framework-managed sessions.

Almost every entry on the list reduces to four habits: validate input, check authorization every time, keep secrets out of code, and update your dependencies.


  
The habits that prevent most of the list

  

    
Never trust input

    
Validate and escape everything from a user, a URL, an API, a file. Lesson 5's whole point. Frameworks help — don't bypass them.

    
Check authorization on every request

    
"Is this logged-in user allowed to do this specific thing to this specific resource?" — server-side, every time. Never trust the client to enforce permissions; it can be bypassed.

    
Least privilege, everywhere

    
Your DB user, API keys, cloud roles, Firebase rules — minimum access each needs. A breach then can't reach what it was never allowed to touch.

    
Keep secrets out of the code

    
API keys and passwords go in environment variables / secret managers, never in the source (and never in a public repo or client-side JS — anyone can read it).

    
Patch your dependencies

    
Run an audit (e.g. npm audit), keep libraries current, watch for advisories. You ship their bugs too.

  


  

    
For RoShop & Atlas, specifically

    
1. Your Firebase security rules ARE your access control — default-deny, then allow exactly what each user needs (this is "broken access control" made concrete). 2. No API keys or secrets in any committed file or client-side script — Atlas is public source. 3. You already do dependency hygiene in the quant repo (pinned requirements.txt) — same discipline for any web project.

  


  
Recap

  
The OWASP Top 10 names the bugs that breach people most, but they collapse into a few habits: validate input, check authorization every request, least privilege, secrets out of code, patch dependencies. Secure coding isn't a separate skill bolted on at the end — it's a handful of defaults you build in from the first line.
