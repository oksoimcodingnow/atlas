Lesson 5 · Attacks & defenses

The bugs that break the web.

Most real breaches aren't Hollywood hacking. They're a website that trusted input it never should have. Three classic mistakes cause an enormous share of them, and the fixes are almost embarrassingly small once you see the pattern.

~9 min · interactive · builds on Lessons 1–4 · most useful lesson if you build web apps

You build web apps (RoShop, Atlas). That makes this the lesson with your name on it. Every attack here comes from one root sin: treating user input as trusted. A user can type anything into a form, a URL, a search box — and if your code treats that text as a command instead of as data, it can be turned against you.

The three classics — defined

SQL injection (SQLi)
Your code builds a database query by gluing user input into a command string. An attacker types input that closes your query and adds their own — dumping the whole user table, or logging in as admin without a password. The breach behind countless "50 million accounts leaked" headlines.
Cross-site scripting (XSS)
Your page displays user input without cleaning it. An attacker submits input that is JavaScript (e.g. in a comment or username); when another user views the page, that script runs in their browser, as them — stealing their session, their data, their account.
Cross-site request forgery (CSRF)
A malicious page tricks your already-logged-in browser into firing a real request to a site you trust ("transfer money," "change email") without you meaning to. It abuses the fact that your browser auto-sends your cookies.

See SQL injection, safely

Below is a simulated login that builds its query the unsafe way (this runs entirely in your browser — nothing real is touched). Try logging in as admin with any password. Then try the classic injection in the username box: admin' --

Vulnerable login (simulation)
The server builds: SELECT * FROM users WHERE name='INPUT' AND pass='...'

See what happened? The -- starts a SQL comment, so everything after it — including the password check — is ignored. You logged in as admin without knowing the password. The ' OR '1'='1 trick makes the WHERE clause always true. The database did exactly what it was told; the bug is that your code let the user write part of the command.

The fix is one idea: never glue input into commands

Use parameterized queries (a.k.a. prepared statements). You write WHERE name = ? and hand the input separately, as data. Now admin' -- is treated as a literal (weird) username that simply doesn't exist — the database never parses it as code. Every modern database library supports this. The rule: data is data, never code.

Every web attack here is the same sentence: the code mistook the user's data for the code's commands. Keep those two apart and most of them vanish.

The defender's checklist (yours, for RoShop/Atlas)

Validate & escape all input/output
Never trust what comes from a user. Escape on the way out (XSS), parameterize on the way to the database (SQLi). Frameworks do most of this for you if you don't fight them — e.g. React escapes by default; the danger is dangerouslySetInnerHTML.
Least privilege
Your database user, your API keys, your Firebase rules — give each the minimum it needs. If the shop's web code can only read products, an injection can't drain accounts.
Lock down your Firebase rules
This is your real-world one. A wide-open database rule is the cloud-era equivalent of SQLi — anyone can read/write everything. Default-deny, then allow exactly what each user needs (Lesson 11 goes deeper).
Use the framework's protections
CSRF tokens, same-site cookies, Content-Security-Policy headers — modern frameworks ship these. Turn them on; don't roll your own.

Recap

The biggest web breaches come from one root cause: trusting user input as if it were code. SQLi injects database commands (fix: parameterized queries). XSS injects browser scripts (fix: escape output). CSRF rides your logged-in session (fix: tokens + same-site cookies). The unifying rule a defender repeats forever: data is data, never code.
